## Problem Statement

You're the scrum master for an 8-person team. Each morning before standup you want a 5-minute pre-read that tells you who's stuck, who shipped, who's overloaded, and who needs unblocking. Today this requires opening 4+ tabs (Jira, GitHub, Slack, Calendar) and pattern-matching across them in your head. You want it pre-digested, daily, persisted to a Google Sheet, and DM'd to you on Slack.

## What Makes This Cool

- **The sheet IS the dashboard.** Dates as rows, teammates as columns. Open Google Sheets → see today's column, scroll left → see the trend. Zero infra to build a UI.
- **Claude does the synthesis.** Raw API output is noise; the value is *"Sarah's PR has been waiting on Mike for 3 days"* — phrased like a teammate would say it.
- **Native to your existing harness.** Uses MCPs you already have authenticated (Atlassian, GitHub, Slack, Google Drive) and Claude Code's `CronCreate` for scheduling. No deploy, no hosting, no separate app.

## Constraints

- Runs locally as a Claude Code scheduled task (`CronCreate`).
- 8 people, one Jira project (AP), one GitHub org (ChronusCorp).
- Storage = Google Sheet (you supply the ID). Schema: rows = dates, columns = teammates, cells = signals + narrative.
- Output = Slack DM to you + sheet row.
- Identity mapping = static JSON config (one-time, ~32 lines for 8 people).
- LLM = Claude API direct (Sonnet 4.6 for cost, Opus only if narrative quality is poor).
- Tool code lives **outside** the `groups` repo (e.g. `~/projects/team-pulse/` or `~/.claude/team-pulse/`).
- No DMs, no private channels, no personal calendars.

## Premises (challenge anything you disagree with)

1. **The Google Sheet IS the dashboard.** Don't build a web dashboard until you've used the sheet for 4 weeks and identified what it can't do. Sheets has filters, conditional formatting, charts.
2. **Identity mapping = manual JSON config.** 8 people × 4 systems = 32 lines you can write in 5 minutes. Auto-bootstrap (matching display names across GitHub/Jira/Slack) is brittle and costs hours.
3. **MVP excludes Slack message scraping.** Slack is the noisiest signal source ("@here lunch?" is not a blocker). Defer to v2 once the rest is stable.
4. **MVP excludes Google Calendar.** No MCP exists for it; using the API requires service account setup. Defer to v2.
5. **Daily-only, not real-time.** One run, 8:00 AM. No streaming, no webhooks.
6. **Narrative is short.** Each person gets 2-3 sentences max + a structured signal block. No essays.

## Data Source Map

### Jira (via `mcp__atlassian`)

**Pull:**
- Open tickets per assignee — `searchJiraIssuesUsingJql`
  - JQL: `project = AP AND assignee in (accountIds) AND statusCategory != Done ORDER BY updated DESC`
- Status transitions in last 24h — `searchJiraIssuesUsingJql`
  - JQL: `project = AP AND assignee in (accountIds) AND updated >= -1d`
  - Then `getJiraIssue` per result → read changelog → derive transitions
- Time-in-current-status — derived from changelog timestamps
- Comments in last 24h — `getJiraIssue` → comments field
- Blocker labels/status — JQL: `(labels = blocked OR status = Blocked) AND assignee in (accountIds)`

**Noise to filter:**
- Tickets in "Done" status older than 24h
- Status changes the assignee made on their own tickets (not a stuck signal)
- Bot/automation comments (filter by author = automation account)

### GitHub (via `mcp__github`)

**Pull:**
- Commits in last 24h per author — `list_commits` with `since=24h`
- PRs opened/merged/closed in last 24h — `list_pull_requests` filtered by `updated_at`
- Draft PRs idle >3 days — `list_pull_requests` then filter `draft=true && created_at < now-3d`
- PR review state — `pull_request_read` per PR → `reviewDecision`, `reviewThreads`, `lastActivityAt`
- Reviews given to teammates — `search_pull_requests` with `reviewed-by:USER updated:>=YESTERDAY`

**Noise to filter:**
- Dependabot / GitHub Actions / bot commits
- Pure merge commits with no authored work
- Archived/private repos outside scope

### Confluence (via `mcp__atlassian`)

**Pull:**
- Pages created/edited last 24h — `searchConfluenceUsingCql`
  - CQL: `lastModified > -1d AND contributor in (accountIds) AND type = page`

**Noise:** templates, scratch/personal-space pages.

### Slack (via `mcp__claude_ai_Slack`) — DEFERRED to v2

Why deferred: signal-to-noise is poor; identity mapping is hardest here (real_name vs display_name vs email vs userId); high false-positive rate. Add when v1 is stable.

### Calendar — DEFERRED to v2

No native MCP. Adding requires Google service account + Calendar API setup. Not worth the complexity in week 1.

### Storage

- **Google Sheet** (write via `mcp__claude_ai_Google_Drive`):
  - Rows = dates (YYYY-MM-DD)
  - Columns = teammate display names
  - Each cell = markdown blob: signals block + narrative paragraph
- **Local SQLite** (`~/.team-pulse/state.db`):
  - Caches "last seen state" per ticket/PR
  - Used to compute deltas (e.g., "this PR has been idle 36h since last activity")
  - Lets you run the digest twice in one day without double-counting

### Slack delivery

- `mcp__claude_ai_Slack__slack_send_message` to your DM
- Format: collapsible per-person sections; "🚩 needs attention" people surfaced first

## Approaches Considered

### Approach A: Claude Code cron + MCPs **(RECOMMENDED)**

- `CronCreate` schedules daily 8:00 AM run
- Single Claude prompt (~150 lines, in `~/.claude/team-pulse/digest.md`) invokes MCPs to gather data, calls Claude API for synthesis, writes to sheet, sends Slack DM
- Config files: `team.json` (identity map), `config.json` (sheet ID, thresholds, Slack DM channel)
- **Effort:** human ~1 week / **CC: ~2-3 hours**
- **Risk:** Low
- **Completeness:** 9/10
- **Pros:** Native to your harness; MCPs already authenticated (zero OAuth); no Python deps; hand-off = "share the folder + run `claude --dangerously-skip-permissions`"; cron + secrets handled by Claude Code
- **Cons:** Tied to Claude Code; harder to debug than a Python script; long prompt latency (10-30s per run)
- **Reuses:** existing Atlassian/GitHub/Slack/Google Drive MCPs, Claude Code cron, your existing skill ecosystem

### Approach B: Python script + crontab

- Standalone Python in `~/projects/team-pulse/` with `.venv`
- SDKs: `PyGithub`, `jira-python`, `slack-sdk`, `gspread`, `anthropic`
- Local `crontab` schedules at 8:00 AM
- **Effort:** human ~2 weeks / **CC: ~4-5 hours**
- **Risk:** Low
- **Completeness:** 10/10
- **Pros:** Explicit; debuggable; portable to any laptop without Claude Code; testable with pytest; secrets via macOS keychain or AWS Secrets Manager
- **Cons:** 4× the code; dependency management; 4 separate auth tokens to provision and rotate; you re-implement work the MCPs already do
- **Reuses:** nothing from your existing setup

### Approach C: Hybrid — Python data layer + Claude API synthesis

- Python deterministically pulls + normalizes data
- Pipes JSON to Claude API for narrative synthesis only
- Cron-scheduled
- **Effort:** human ~3 weeks / **CC: ~6-8 hours**
- **Risk:** Low
- **Completeness:** 10/10
- **Pros:** Clean separation; fast deterministic data layer; LLM only for the part it's good at
- **Cons:** Most code; two systems to maintain; slowest to ship

### Recommendation: **Approach A**

You already have all 4 MCPs authenticated — zero auth setup. Claude Code gives you cron, secrets, and execution for free. For an 8-person personal tool, B and C are over-engineered. If A starts feeling clunky after 2 months (you want unit tests, you want to share the tool with another scrum master, narrative quality drifts), that's the signal to migrate to C.

`★ Insight ─────────────────────────────────────`
- **MCPs vs SDKs trade-off**: MCPs are slower per call (~500ms-2s) than direct SDK calls (~100-500ms), but the *integration* time saved (auth, retries, schemas) is enormous. For a daily run on 8 people, MCP latency is invisible; SDK setup time is days.
- **The "narrative" cell is the moat**: anyone can dump JSON into a sheet. The reason this tool gets used is because the LLM-written paragraph saves you 30 seconds of synthesis per teammate. Get that prompt right and the rest doesn't matter.
- **Claude Code's `CronCreate` is the unsung hero here**: deferred-tool-loaded, headless, runs prompts unattended, and inherits your full MCP setup. This makes Approach A possible. If `CronCreate` couldn't invoke MCPs in headless mode, you'd be stuck with B.
`─────────────────────────────────────────────────`

## Privacy & Transparency Plan (minimal — solo tool)

You said this is solo and non-shared. Minimal posture:

- **Don't read DMs, private channels, or 1:1 calendar invites** — the data sources above don't, by construction
- **Sheet is restricted to your account only** — share with no one, not even "anyone with link"
- **No hardcoded credentials anywhere** — MCPs handle all auth via your existing Claude Code config
- **One-line team mention** (recommended, not required): *"FYI I'm trying out a daily digest tool that pulls from our public Jira/GitHub/Confluence to help me prep for standup — let me know if anything feels off."* Cheap insurance against awkwardness if a teammate sees your screen later.

## MVP Definition (Week 1) — ship this, resist scope creep

**Must include:**

- [ ] Static `team.json` with 8 entries × 4 fields (`name`, `github_login`, `jira_account_id`, `slack_user_id`)
- [ ] `CronCreate` schedule at 8:00 AM daily
- [ ] Pull Jira: open tickets, status changes (24h), blocker labels
- [ ] Pull GitHub: commits, PRs opened/merged, draft PRs >3d, PR review state
- [ ] Pull Confluence: pages created/edited (24h)
- [ ] Apply 6 of 7 blocker rules (skip Slack rule):
  - Jira ticket idle >4 working days → flag
  - PR open >36h zero reviews → flag
  - PR with reviews, no author response >24h → flag
  - ≥3 in-progress tickets per person → flag
  - "Blocked" label/status → flag immediately
  - (deferred: Slack mention threshold)
  - (deferred: meeting hours threshold — needs Calendar)
- [ ] Surface positive signals: PRs merged, helpful reviews given, tickets closed, docs shipped
- [ ] Claude API (Sonnet 4.6) writes 2-3 sentence narrative per person
- [ ] Append row to Google Sheet (`Date | member1 | member2 | ... | member8`)
- [ ] Send Slack DM with formatted digest (🚩 attention people first)

**Explicitly NOT in MVP:**
- ❌ Slack message scraping
- ❌ Google Calendar
- ❌ Web dashboard
- ❌ Trend detection (need history first)
- ❌ Per-person threshold customization (defaults are fine)
- ❌ Sprint-aware filtering

## Phased Roadmap

**v1 — MVP — Week 1**
Above. Static rules, structured signals, basic narrative.

**v2 — Weeks 2-3**
- Google Calendar (meeting hours, focus blocks, "back-to-back days")
- Slack public-channel signals (mentions of `@channel/@here` without responses; keyword detection on "stuck", "blocked", "anyone know")
- Trend detection: 7-day moving averages for review turnaround, idle time, in-progress count
- Smart thresholds: *"Sarah's review turnaround is 2× her own 30-day baseline"* instead of fixed 24h

**v3 — Weeks 4-6**
- Cross-team dependency surface: PRs blocked on people outside your 8
- Sprint-aware tagging: "in this sprint" vs "spillover"
- Lightweight web view (just `https://docs.google.com/spreadsheets/...` with saved chart filters — still not a custom dashboard)
- Optional: a `/standup` slash command that posts a redacted version to your team Slack channel (only after you've used it solo for a month)

## Success Criteria

- You read the digest in <5 minutes before standup
- It surfaces ≥1 actionable signal per week you'd have otherwise missed
- False positive rate <20% (you don't lose trust in the alerts within the first 3 weeks)
- After 4 weeks, you find yourself opening the sheet to look at trends without prompting

## Open Questions / Risks

1. **Identity mapping accuracy** — if a teammate's GitHub display name doesn't match Jira, you'll silently miss their data. **Mitigation:** validate the JSON by running the digest manually for one person first; cross-check counts against the actual Jira/GitHub UIs.
2. **CronCreate headless MCP support** — verify Claude Code's cron can invoke MCPs without an active session. If not, fallback is Approach B. **Pilot this on day 1.**
3. **Google Sheet write reliability** — silent auth/quota failures lose history. **Mitigation:** append a success log line to local SQLite each run; alert if 2 consecutive runs fail.
4. **MCP rate limits** — for 8 people × 1 daily run, very unlikely. Watch for 429s in the first week.
5. **Narrative drift / quality** — first week's LLM summaries will be hit-or-miss. **Mitigation:** budget 2-3 prompt revisions in week 1; capture a few "bad" outputs and add them as negative examples.
6. **Stale identity map** — when someone joins/leaves the team, the JSON is stale and you'll miss data or include ghosts. **Mitigation:** none for MVP; add a quarterly reminder.

## Pilot Plan

**Before scaling to 8:** run for 3 days on yourself + 1 teammate. Verify:

- Identity map resolves correctly across all 4 systems
- Signals match what you'd see manually in the actual Jira/GitHub UIs
- Slack DM lands and is readable
- Sheet row appears at the right cells, no truncation
- Narrative is useful, not noise

If pilot survives 3 days, expand to 8.
